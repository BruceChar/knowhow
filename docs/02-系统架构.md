# Knowhow V2 系统架构

## 1. 架构决策

- 模块化单体，保持单部署单元，不拆微服务。
- PostgreSQL 是业务事实、知识、交互和审计的唯一事实源。
- 前端采用独立 HTML/CSS/JavaScript 资产，不继续维护巨型内联单页。
- 一客户一数据库实例；暂不实现共享多租户 SaaS。
- LLM 可选，无模型时仍可使用已发布知识完成可追溯抽取式回答。

## 2. 分层

```text
Web
  Today / Workbench / Knowledge / Review / Team
          │
HTTP API + Session + RBAC + CSRF
          │
Application services
  Setup / Knowledge / Assistant / Dashboard / Team
          │
Domain
  Knowledge / Interaction / Gap / Policy / Readiness
          │
Infrastructure
  PostgreSQL / LLM provider / migration / backup
```

依赖只能由外向内，路由不得直接写复杂 SQL，业务规则不得依赖页面结构。

## 3. 核心领域对象

| 对象 | 作用 |
|---|---|
| Organization | 企业、行业、默认语言和配置 |
| Account | 老板、业务员、知识负责人、管理员 |
| Team | 产品线、区域或业务小组的数据边界 |
| AccessRole | 可配置功能权限与默认角色模板 |
| KnowledgeUnit | 各类知识及版本、来源、风险和有效期 |
| AnswerRule | 语言、语气、风险升级和回答结构规则 |
| Interaction | 客户问题、AI 草稿、最终答案、发送状态与修改差异 |
| KnowledgeGap | 无法回答、回答错误或需要补充知识的问题 |
| Evidence | 知识来源和可追溯证据 |

知识与证据统一使用 `organization`、`team`、`private` 三种范围。功能权限和
数据范围分别在 API 与查询层执行，不能只靠前端隐藏按钮。

## 4. 回答流程

```text
问题理解
→ 公司权限与数据范围
→ 检索已发布知识
→ 检查风险与业务事实
→ 应用回答规则
→ 生成草稿或升级人工
→ 记录 Interaction
→ 业务员编辑后标记发送
→ 修改差异和缺口进入学习闭环
```

## 5. 部署

```text
Browser
   │
Knowhow App（FastAPI + 静态资产）
   │
PostgreSQL
```

开发环境使用 Docker Compose。生产安装器后续提供：

- 预检、初始化、迁移、健康检查一体化。
- 定时备份和恢复演练。
- 企业向导与知识导入向导。
- 独立客户部署包，不共享数据库。

## 6. 可观测性

最小指标：

- API 错误率和响应时间。
- 问答命中、升级和人工修改比例。
- 知识发布、缺口、过期和审核等待时间。
- 最近失败任务与数据库/LLM 健康状态。

## 7. 当前技术边界

P1 已使用本地 bge-m3 生成 embedding，通过 pgvector HNSW 召回 Top 候选，再与
Jieba 关键词结果进行加权 RRF 融合。模型不可用时自动降级为关键词检索。

直接连接企业微信、WhatsApp、邮件和 CRM/ERP 仍属于 P2；P1 导入的是这些系统
导出的 CSV/TXT/Markdown 文件。
