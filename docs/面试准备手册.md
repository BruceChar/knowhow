> **定位**：AI 应用 / 技术工程岗 · 技术负责人视角 · RAG 落地 + 知识控制层

# 第一层：技术实现高频追问 + 答案

## T1. 混合检索具体怎么实现？为什么之前的关键词路是失效的？

**答案**：`src/core/search.py` 两路召回 + 加权 RRF 融合：

1. **向量路（语义主力）**：bge-m3 本地 embedding（1024 维）→ pgvector 余弦相似度，HNSW 索引。对同义改写、中英混杂强。
2. **BM25 路（词面兜底）**：jieba 中文分词 → 经典 BM25 打分（k1=1.5, b=0.75）。对货号/型号/精确词命中强。

**踩过的坑（讲清楚才有深度）**：原关键词路用 PG 内置 `ts_rank(to_tsvector('simple', ...))`——`simple` 配置**不做中文分词**，中文问句实际是失效的。我重构成 jieba + Python BM25，中英文、货号都有效。

融合用**加权 RRF**（Reciprocal Rank Fusion）：`score = Σ w·1/(K+rank)`，K=60，向量权重 1.0、BM25 权重 0.5——两路异质，向量语义为主导、BM25 词面作辅助，弱 BM25 匹配不能挤掉向量路强项。

## T2. 中文检索怎么处理的？

**答案**：三层各司其职：
- 中文语义 → bge-m3 多语言向量（中英混杂效果好，黄金集有专门样本验证）；
- 中文词面/型号 → jieba 分词 + BM25（不是 PG 分词扩展，纯 Python 实现，零编译依赖、跨平台）；
- 候选预筛 → ILIKE 词命中（任一 query 词命中 question/answer/category 才进候选）。

关键词路的候选集 = 治理过滤后且至少命中一个 query 词的 FAQ，在候选语料上现算 df/avgdl 打分——避免全库扫描，且打分口径与语料一致。

## T3. 两路融合为什么用加权 RRF？参数怎么定的？

**答案**：RRF 不需要跨路分数归一化（向量余弦和 BM25 分数量纲完全不同，直接加权求和没法比）。用 rank 转分数天然可比。参数调优过程（有真实 A/B 证据）：

| 版本 | Recall@5 | MRR@5 | 问题 |
|---|---|---|---|
| 纯向量（基线） | 1.0000 | 0.9450 | 词面查询鲁棒性弱 |
| 混合 v1（RRF 等权，BM25 候选 20） | 0.9825 | 0.9444 | GS2-005 退化：BM25 弱匹配项（discount/custom prototype 类）叠加挤掉向量路理想答案 |
| 混合 v2（加权 RRF 1.0/0.5 + 30% 质量门槛 + BM25 精取 k 条） | 1.0000 | 0.9465 | 持平召回 + MRR 微升，0 miss |

**关键设计**：向量候选放宽到 4k（语义召回宽），BM25 候选精取 k 条（词面本来就精确，多了全是弱匹配噪音）；BM25 路加 30% 相对质量门槛（低于 top 得分 30% 的不参与融合）。这是"防弱匹配挤占"的工程答案。

## T4. 混合检索相比纯向量到底收益在哪？

**答案**：从黄金集指标看是持平（1.0）+ MRR 微升（0.945→0.9465）——因为纯向量在 57 条上已经全命中。但**冒烟测试证明了两路互补**：
- "What is your MOQ"：BM25 精确命中（7.77 高分）双路融合排第一；
- "PS-2000 型号"：BM25 词面命中；
- "交期多久"：BM25 空（词面无重合），向量路兜底返回语义相关。

**面试口径**：混合检索的价值不是把已满分的数据再刷高，而是**鲁棒性**——词面命中的问句（货号/型号/精确词）在向量偶发失准时有人兜底。数据量放大到真实手册级（长文本）后差距会更明显。评判混合检索要用"两路各命中哪些 case"分析，不能只看总分。

## T5. 过滤为什么前置进同一 SQL？不是先检索后过滤吗？

**答案**：**先检索后过滤会损失召回**——向量只取 top-K，被过滤掉的记录可能占着高相似度位次，过滤后有效结果不足 K。我们把权限/有效期/状态过滤和向量检索放进**同一 SQL 的 WHERE**（`_base_where`：approved 视图 + valid_from/valid_until + permission = ANY + 可选 customer_ready），过滤后排序取 top，还避免了"两套存储一致性"问题。代价是过滤字段要有索引（permission/valid 都低基数，pgvector 配合 HNSW 没问题）。过滤后的 Recall@5 用黄金集实测 1.0——不是默认无损，是基准测试证明的。

## T6. 评测体系：三层指标和门禁阈值？

**答案**（`src/core/eval_runner.py`）：
- **检索层**：Recall@5 = 命中 case 数 / 总数；Precision@5 = 命中数 / (总数×top_k)；MRR@5 = 理想答案命中排位倒数均值。**口径提示**：单理想答案时 Precision@5 上限是 1/5=0.2，所以同时看 MRR，避免误读；
- **事实层**：fact_accuracy = 检索命中 case 中答案与黄金集期望一致的比例（黄金集答案即话术库原文，确定性校验；预留 LLM 抽取校验接口）；
- **红线层**：red_line=True 的 14 个 case（价格/交期/认证/低报/客户名单等）必须 100% 命中且事实正确，**错一条即门禁失败**。

门禁阈值：Recall≥0.9、MRR≥0.5、Fact≥0.9、红线=0。评测结果持久化 `eval_report` 表可回溯历史版本。**为什么 57 条够**：按 35 模块分层抽样做发布基线，全量可靠性靠真实会话 shadow 数据回流继续扩充。

## T7. 红线规则引擎怎么设计的？（为什么不用模型自觉）

**答案**（`src/core/gate.py`）：规则代码化，**不依赖模型判断**，优先级固定：
1. **红线正则命中 → D 阻断**（8 条规则覆盖 14 个用例）：违法/走私/洗钱/偷税漏税；个人账户/第三方退款；低报货值；客户名单/护照/验证码；复制 logo/侵权；保证/百分百/终身保修；成本价/出厂价/最低价；
2. **无已批准知识可引 → D 拒答**（禁止编造）；
3. **高风险知识卡 → C 升级（need_tool）**；敏感字段（定金/预付款/合同/独家/专利/认证）→ C；
4. **涉及报价/交期 → B + 工具核验**；中风险/新客户 → B；
5. 低风险且证据完整 → A 自动。

每层都有明确 reason 写入审计，可解释可追溯。**面试亮点**：有一次真实拦截——切换 Qwen3 embedding 时红线用例未命中、门禁 FAIL，发布被拦下（旧评测报告可查）。

## T8. RBAC 权限模型怎么设计的？

**答案**：`system_` 前缀表（system_account / system_role / system_account_role / system_role_permission），4 张表：
- **权限点**：22 个，按"模块→页面→功能"权限树组织（如 faq.view / faq.edit / faq.review / ingest.view / role.manage / account.manage / agent.use），管理端按树勾选分配；
- **角色**：可创建、分配权限、**派生**（复制权限再追加，如"技术"→"技术1"加一项 faq.review）、**重命名**（技术1 → 技术经理）；data_scope 分 full / standard（public+internal）；
- **账户**：默认双账户 admin/admin（管理员，22 权限 full）、editor/editor（业务员，12 权限 full）；登录即绑定角色；
- **停用保护（双保险）**：内置 admin 账户不可停用；停用任何 account.manage 权限账户时校验必须仍存在启用的管理员，否则拒绝——防止"管理员把所有人锁死"事故；
- **改密入口**：自助改密（8 位起）+ 管理员重置（重置后强制首登改密、注销会话）；pbkdf2 260k 迭代哈希、会话 24h TTL、登录失败 5 次锁 10 分钟、CSRF 校验。

## T9. 一次回答的完整链路？

**答案**：
```
客户消息/业务员问题
 → 混合检索（向量 + jieba BM25，同一 SQL 治理过滤：approved/有效期/权限/customer_ready）
 → 门禁 decide(question, cards, context)：
     红线命中 → D 阻断；无知识可引 → D 拒答
     高风险卡/敏感字段 → C 升级；涉及报价 → B + 工具；中风险/新客户 → B
     低风险且证据完整 → A 自动
 → 输出 auto / draft / escalate / block（audit_log 记录 decision/action_level/citations/latency/model）
 → 人工修改回流 issue 表（知识缺口不自动发布）
```

## T10. 防幻觉机制汇总？

**答案**：四层。**检索侧**：只让模型基于 approved 且未过期的知识作答；**事实侧**：动态事实（价格/交期）走接口或已审批快照，静态事实绑 sources 证据编号，无证据强制拒答；**门禁侧**：A/B/C/D + 红线规则引擎；**评测侧**：黄金集三层评测作发布门禁，红线 0 错误。

## T11. 为什么选 PG+pgvector，不用 Milvus/Qdrant？

**答案**：数据量（402 条 FAQ + 1,500 SKU，十万向量以内）用独立向量库是过度设计。PG+pgvector 让**向量和治理数据（状态/有效期/权限/风险/审批）在一个事务、一套 SQL 里**，过滤和检索同库执行，避免两套存储一致性难题。我们的核心是数据治理不是检索吞吐。规模上来再拆独立向量库，且 embedding / vector store 都做了防腐层抽象（`embedding_provider.py`），可迁移。

## T12. embedding 为什么选 bge-m3？

**答案**：**黄金集实测选型，不拍脑袋**。bge-m3（本地，1024 维，多语言，中英混杂强）在黄金集上 Recall@5 达标 0.5（6 条小样本期）→ 扩充到 50 条后 0.8 → 57 条 v2 全量 1.0 / MRR@5=0.945。对比的候选模型（Qwen3-Embedding 系列，编码更快、维度同为 1024）在小样本期 Recall@5 低于 bge-m3，且红线用例未命中、评测门禁 FAIL——被拦截。**面试口径**：检索质量优先于编码速度（答错比答慢代价高）；换模型必须重跑完整评测，门禁不是摆设。模型本地部署，客户数据不出本地。

## T13. pytest 自动化测试覆盖了什么？

**答案**：73 用例分两类：
- **纯函数 63 个**（默认 `pytest` 跑，不依赖外部服务）：jieba 分词、BM25 打分（词命中/长度归一/idf 方向）、加权 RRF（权重方向、双源叠加）、治理过滤 SQL 参数顺序、红线 8 条规则逐条、动作分级分支、pbkdf2 哈希（盐/错误拒绝/畸形串）、评测命中判定、数据范围子句；
- **API 冒烟 10 个**（`pytest -m integration`，服务不可达自动 skip）：登录/me、权限隔离（editor 越权 403）、CSRF 校验、**管理员停用保护**、角色 CRUD + 派生 + 重命名。

**测试驱动的真实修复**（讲这个有说服力）：写测试时发现交期英文问句（delivery time）没被识别为动态事实——门禁词表补了 delivery/shipping；还发现停用账户登录会 500——login 补了 disabled 分支返回 403。测试不是摆设，是真的抓 bug。

# 第二层：方案与业务高频追问 + 答案

## S1. 为什么不用 RAGFlow/Dify 这类开箱即用平台？

**答案**：研究过，结论"借鉴但不直接采用"。通用文档问答平台没有外贸的 sku/variant/offer 实体、审批链、风险分级、领域评测集——这些是客户付费的理由。我们的差异化是**知识控制层**：哪条知识能用（approved+有效期）、谁能批准（审批流+RBAC）、什么能自动发（A/B/C/D 门禁）、错了怎么追责（红线规则 + 审计留痕）。基础设施用成熟组件（pgvector、sentence-transformers），差异化自己写（知识模型、门禁、评测、审批流）。客户只需要通用文档搜索且有工程师时，开源方案确实更便宜——这不是秘密。

## S2. 产品形态怎么定位？传统管理后台 + Agent 客服系统？

**答案**：这是**一套系统两种界面**的设计：

1. **管理后台（给公司负责人/管理员）**：传统左侧菜单布局——知识卡管理（审核流：入录→草稿→approve/reject）、数据入录（文件上传/批次处理）、评测面板（黄金集指标/历史报告）、权限管理（角色/权限树/账户）、审计日志。负责人在后台看到的是**治理视图**：数据质量、评测指标、谁批了什么、模型答了什么。
2. **Agent 客服/问答入口（给员工与业务使用）**：自然语言提问，混合检索 + 门禁作答，答案带证据编号与动作等级。业务员看的是**使用视图**：能信什么、要确认什么、红线为什么拒答。

**为什么不是一个纯粹的"问答机器人"**：知识要可持续，就必须有治理端——没有审批、权限、评测，知识库半年就烂掉（口径冲突、过期认证、责任人消失）。**为什么不是一个纯粹的管理后台**：没有问答入口，知识库只是静态文档库，员工不会去检索。两者闭环：后台治理 → 前端作答 → 审计回流 → 后台改进。

**权限下放的设计**：负责人把数据录入/审核权限按角色分给员工（如"技术"角色可录知识卡+审核技术类，派生"技术经理"加审核权限），员工录入知识沉淀、负责人只管兜底审批与指标——知识共建而不是知识垄断。

## S3. 权限为什么要下放给员工？数据怎么治理？

**答案**：企业知识在资深员工的脑子里和电脑里，**不让他们录入，系统就没有可持续的数据源**。所以设计是：
- **职责分离**：录入的人（faq.edit）≠ 审核的人（faq.review）≠ 使用的人（faq.view/agent.use）；账号绑定角色，角色可派生（"技术"→"技术1"加一项审核）可重命名（技术1→技术经理）；
- **审批流兜底**：员工录入 → 草稿 → 有审核权限的人 approve → 才进检索；published_snapshot 保留发布快照，版本可追溯；
- **风险分级**：知识卡带 risk_level/action_level，高风险知识即使 approved 也由门禁强制人工确认；
- **审计留痕**：每次回答记录 decision/citations，谁批准了什么、模型答了什么都可查。

## S4. 商业化路径怎么讲？

**答案**：
- **形态**：SaaS 订阅 + 私有化部署两档（客户数据不出本地是卖点：bge-m3 本地 embedding，LLM 可换本地模型）；
- **试点设计**：90 天两家付费试点——先接一个真实客服渠道（邮件/阿里国际站 TM），用真实流量验证检索与门禁，业务指标到位再谈续费；当前核心链路已验证（评测门禁 PASS），缺的是真实渠道运行数据；
- **定价锚点**：按账号/知识库规模/渠道数收费，实施工时单列（数据治理是重活，客户要为数据服务付费，不能只卖软件）。

## S5. 会被通用大模型/Agent 直接取代吗？

**答案**（诚实且有立场）：
- **短期不会**：通用大模型不掌握企业私有知识，也不敢为企业承诺负法律责任。企业要的不是"能聊天"，是"只答已批准的内容、红线绝不碰、错了有审计"——这是**确定性**需求，大模型的自回归本质给不了；
- **会演进**：我们把自己定位成"知识控制层"，模型可以是任何家（LLM 模型中立，防腐层可换）。通用 Agent 越强，越需要我们的治理层去约束它——知识库、审批、门禁、审计是 Agent 的护栏；
- **真正会被取代的**：纯文档搜索工具（RAGFlow 那类）——那部分我们本来就不靠它赚钱。

## S6. 数据治理：谁提供、谁审批、谁更新？

**答案**：**谁提供**：员工按角色录入（技术录技术知识、客服录话术）；**谁审批**：角色带 faq.review 的人（技术经理/管理员）；**谁更新**：动态事实走接口或 15 天有效期快照，静态事实走新版本（版本化不覆盖旧记录）；**过期**：valid_from/valid_until 自动失效不进检索；**回流**：答错的反馈进 issue 表，人工修改后回流知识卡，不自动发布。数据责任书面确认（用户要求"文档化"）。

## S7. 系统边界？什么情况下不该上？

**答案**：只有通用文档搜索需求且有工程师 → 开源方案更便宜；单人企业/无稳定流程/无知识维护责任人 → 不上（知识库会烂）；要求替换 CRM/ERP/报价系统 → 不做（我们是知识控制层）；不愿提供真实问题和评测数据 → 无法验证，不做。**这是一个"敢说不做"的项目**——边界清楚反而可信。

## S8. 业务指标怎么定义？

**答案**：不把"自动回复率"当核心指标（会鼓励系统在不该答时硬答）。用：新业务员首次正确报价时间（对比基线）、人工修改距离（草稿与最终发送差异）、资深员工被咨询次数、知识更新延迟/复核积压；商业层：付费试点转化、续费意愿、实施工时。

## S9. 如果重来一次，哪些会做得不一样？

**答案**：
1. 黄金集更早建（先定义标杆问题再倒推 schema，避免字段返工）；
2. 业务口径（红线边界、审批流）第一天就和业务负责人对齐；
3. 更早锁定一个真实客服渠道，让链路在真实流量里跑；
4. embedding 服务化更早做（慢的根因是每次重载模型，不是模型本身）。

## S10. 给公司负责人的 1 分钟价值叙事

**答案**："您的新人现在要半年才能独立回询盘，因为知识在资深员工脑子里、在 Excel 里、在 12 本手册里，口径还不一致。这套系统把 402 条话术和全部产品知识结构化沉淀，员工用自然语言问，系统只从已批准的知识里答——新人第一次报价不用猜，红线问题（成本价、过度承诺）系统直接拦住，谁批准了什么、答了什么全程留痕。您不需要技术团队维护，权限分给员工自己录入，您在后台看评测指标和数据质量就行。先接一个真实渠道跑 90 天，用数据说话，再决定铺开。"
