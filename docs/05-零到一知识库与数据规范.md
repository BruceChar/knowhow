# 新公司从 0 建库与数据规范

## 1. 上线不是先建 20 张表

企业真正需要按以下顺序完成：

1. 建立公司、负责人和默认角色。
2. 明确哪些资料能进系统、哪些属于敏感文件。
3. 导入原始资料并保留来源。
4. 把资料规范化为知识、产品和规则。
5. 业务负责人补全高风险知识。
6. 审核并发布第一批高频问题。
7. 业务员开始使用，系统记录真实问题。
8. 用知识缺口和人工修改持续迭代。

## 2. 分阶段 ETL

```text
来源
→ 原始证据 Evidence
→ 类型识别
→ 字段映射
→ 规范化
→ 候选知识/业务事实
→ 人工审核
→ 发布索引
→ 使用与反馈
```

### P0：人工和文本

- 手工创建知识。
- `Q/A` 文本批量导入。
- 所有内容先进入草稿。

### P1：企业文件

- CSV、TXT、Markdown、Excel。
- 自动识别标题、问题、答案、来源、有效期和风险。
- 映射预览、重复检测和错误行报告。
- 一次导入产生可回滚批次。

### P2：业务系统连接

- 产品目录、变体、报价、交期和认证。
- 企业微信、邮件和 WhatsApp 导出文件。
- CRM、ERP 和报价系统 API。
- 增量同步、过期标记和冲突检测。

## 3. 哪些数据结构现在就要定

系统长期稳定的核心结构应现在定义：

| 结构 | 是否现在定义 | 原因 |
|---|---|---|
| Organization | 是 | 所有数据隔离边界 |
| Account / Team / Role | 是 | 人员流动和权限基础 |
| KnowledgeUnit | 是 | 统一知识主对象 |
| Evidence | 是 | 所有导入和审核可追溯 |
| Interaction | 是 | AI 草稿、最终答案和业务价值度量 |
| KnowledgeGap | 是 | 真实问题驱动知识迭代 |
| AnswerRule | 是 | 语言、风险和表达策略 |
| Product / Variant / Price | 是，独立建模 | 不能混在 FAQ 文本里 |
| Training / Readiness | P1 | 依赖真实问答和岗位场景 |
| Connector / SyncJob | P2 | 依赖具体外部系统 |

## 4. 不建议统一成一张大表

`knowledge_unit` 统一管理知识元数据和发布状态，但内部仍有明确类型：

- FAQ
- 产品知识
- 公司规则
- 场景手册
- 客户案例
- SOP

价格、成本、客户资料等结构化事实应使用独立表和受控工具，不能作为普通文本交给 LLM。

## 5. 新公司首日交付标准

- 公司、负责人、默认团队和角色可用。
- 至少一个业务员账户可登录。
- 导入 20 条高频问答作为草稿。
- 负责人可在 10 分钟内审核首批内容。
- 业务员能提问、编辑答案并记录已发送。
- 老板能看到缺口和上线准备度。
- 所有敏感知识有明确可见范围。
